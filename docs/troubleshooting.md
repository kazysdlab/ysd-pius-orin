# PIUS トラブルシューティング

症状から原因と対処を探すためのガイドです。ログや画面に出る文言は、コードに書かれているとおりに載せているので、表示された文をそのまま検索できます。

- 仕様の詳細は [specification.md](specification.md) を参照してください。
- 「ホスト」は Jetson 本体の端末、「コンテナ」は `docker exec -it roscar2 bash` で入った端末です。

## 1. 起動とビルド

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| `docker compose up -d` が失敗し、`/dev/video0` が見つからない旨のエラー（例：`error gathering device information while adding custom device "/dev/video0": no such file or directory`） | CSI カメラがホストに認識されておらず `/dev/video0` がない。`docker-compose.yml` はこのデバイスをコンテナに渡す設定のため、存在しないとコンテナを作れない | ホストで `ls /dev/video*` を確認。電源を切ってからカメラのフラットケーブルを挿し直し、再起動する。カメラなしで一時的に動かすときは、`docker-compose.yml` の `/dev/video0` の行をコメントアウトして `use_dummy_camera:=true` で起動する |
| 同様のエラーで `/dev/ttyTHS1` や `/dev/i2c-7` が見つからない | ホストにそのデバイスがない | ホストで `ls -l /dev/ttyTHS1 /dev/i2c-7` を確認 |
| `start_system.sh` で `-> [警告] 権限の付与に失敗しました。シリアル送信はDRY RUNモードで起動します。` | `sudo` のパスワード入力の誤り・中断、または `/dev/ttyTHS1` がない | 実車を動かすならホストで `sudo chmod 777 /dev/ttyTHS1` を実行し、起動し直す（権限は Jetson の再起動で元に戻ります） |
| `start_system.sh` で `-> [エラー] Dockerコンテナの起動に失敗しました。` | `docker compose up -d` の失敗（デバイス不足、ポート使用中、Docker 権限など） | 直前に出た Docker のエラー文を確認し、この表の該当行へ |
| `permission denied while trying to connect to the Docker daemon socket` | 実行ユーザーが docker グループに入っていない | `sudo` を付けて実行するか、ユーザーを docker グループに追加して再ログイン |
| `Bind for 0.0.0.0:8080 failed: port is already allocated` | ホストの 8080 番を別のプログラムが使用中 | ホストで `sudo ss -ltnp \| grep 8080` で使用中のプロセスを確認して止める。変える場合は `config.yaml` の `dashboard.port` と `docker-compose.yml` の `ports` を両方変更 |
| `No such container: roscar2` / `container ... is not running` | コンテナが起動していない | ホストで `docker compose up -d` を実行（`start_system.sh` なら自動） |
| `install/setup.bash: No such file or directory`、`Package 'pius_control' not found` | ワークスペースが未ビルド、または `setup.bash` を読み込んでいない | コンテナで `cd /home/orin/dev/ws/colcon_ws && colcon build && source install/setup.bash` |
| `colcon build --symlink-install` が `option --editable not recognized` で失敗 | 現在のイメージの setuptools では `--symlink-install` が使えない | `--symlink-install` を付けずに `colcon build` |
| 一度 `--symlink-install` を付けてビルドした後、付けずに `colcon build` しても `option --uninstall not recognized` や `failed to create symbolic link` で失敗する | `build/` に `--symlink-install` の途中の状態が残っている | コンテナ内で `rm -rf build/camera build/control_msgs build/gamepad_msgs` のあと `colcon build`（`build/` の中身はビルドのたびに作り直される中間ファイル） |
| コードを変えたのに動作が変わらない | `--symlink-install` なしのビルドなので、再ビルドするまで古いコードが動く | `colcon build` → `source install/setup.bash` → 再起動。`config.yaml` の変更は再起動だけで反映 |
| コンテナで `pip install` したライブラリが消えた | `docker compose up -d` でコンテナが作り直された（`docker-compose.yml` の変更時など） | 再度インストールする。恒久的にはイメージを再ビルド |

## 2. ダッシュボード

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| `このダッシュボードは Jetson 本体（localhost）と Tailscale 経由でのみ利用できます。` と表示される | ローカルネットワーク（Wi-Fi の IP `172.x.x.x` など）から開いた。**仕様**（ログに `許可していないアドレスからのアクセスを拒否しました: <アドレス>`） | Jetson 本体なら `http://localhost:8080`、他の端末は Tailscale につないで `http://<Jetson の Tailscale の IP>:8080`（ホストで `tailscale ip -4`）。許可範囲は `dashboard.allowed_networks` |
| ブラウザで開けない（Tailscale 経由） | 端末または Jetson が Tailscale につながっていない | 両方で Tailscale を起動し、端末から `ping <Jetson の Tailscale の IP>` で届くか確認 |
| 同上 | コンテナが 8080 番の公開設定より前に作られたまま | ホストで `docker port roscar2` を確認し、8080 がなければ `docker compose up -d` でコンテナを作り直す |
| 同上 | システム（`ros2 launch`）が起動していない、またはダッシュボードノードが起動に失敗し続けている | ターミナルを確認。`OSError: [Errno 98] Address already in use` が 2 秒ごとに出る場合は、コンテナ内で別の launch が動いている。すべて `Ctrl + C` で止めてから起動し直す |
| ヘッダが `通信断`、バナー `ダッシュボードと通信できません。システムが起動しているか確認してください` | ブラウザが 2 秒以上 `/api/state` を取得できない（システム停止、ネットワーク断、ダッシュボードノードの再起動中） | システムが動いているか確認。ダッシュボードノードは 2 秒後に自動再起動するので、数秒待ってから再読み込み |
| 接続状況のランプが `応答なし`、バナー `〇〇が応答していません（ノードが停止している可能性があります）` | そのノードのハートビートが 3 秒以上途絶えている（ノードの異常終了） | ターミナルで `Traceback` やエラーを確認。camera・コントローラーは自動で再起動するが、それ以外（操作解析・モード管理・AI推論・車両シリアル・データ保存）は `Ctrl + C` でシステムごと再起動 |
| ランプが灰色の `起動待ち` のまま | そのノードが一度も状態を送っていない（起動に失敗した、ビルドされていない） | ターミナルの起動ログを確認し、必要なら再ビルド |
| カメラ画像だけ表示されない | 画像が 2 秒以上届いていない（[3章](#3-カメラ)）。または画像の配信が 5 秒以上止まってストリームが切れた | カメラの状態を確認。復旧後にページを再読み込み |
| `index.html` を変えたのに画面が変わらない | 画面ファイルはインストール先から読まれる | 再ビルドして再起動し、ブラウザで再読み込み |

## 3. カメラ

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| 接続状況が `再接続中` のまま。ログに `【接続失敗】CSIカメラを開けません。物理的な接続を確認してください。…秒後に再試行します。(Failed to open CSI camera via GStreamer.)` | ケーブルの接触不良、`nvargus-daemon` の異常、他のプログラムがカメラを使用中 | ① 他にカメラを使うプログラム（別の launch やテスト）を止める。② ホストで `sudo systemctl restart nvargus-daemon`。③ 電源を切ってケーブルを挿し直す。再接続は 1〜5 秒間隔で自動で試みます |
| 通知 `30秒以上再接続できません。ケーブル接続を確認し、改善しなければホストで sudo systemctl restart nvargus-daemon を実行してください` | 上と同じ | 上と同じ。`nvargus-daemon` の再起動後はカメラノードが自動で再接続します |
| 通知 `カメラとの接続が切れました。再接続を試みています（AUTO走行は停止します）` | 走行中の振動などによる瞬断 | 通常は自動で復旧し `カメラに再接続しました` と出る。頻発する場合はケーブルと固定を確認 |
| 通知 `カメラ画像が3秒以上届いていません。カメラノードを再起動します`、状態 `再起動中` | 画像の取得が内部で固まった | 2 秒後にノードが自動で再起動します。繰り返す場合は `sudo systemctl restart nvargus-daemon` |
| 画像の周辺（四隅・左右の端）がピンク色になる | 広角レンズ（Waveshare IMX219-160）に Jetson 標準の ISP 補正が合っていない | ホストで `sudo ./tools/camera_isp.sh install`（メーカーの補正ファイルを導入）。元に戻すときは `remove`。補正後はモデルへの入力の色が変わるため、データを集め直して再学習するのが確実です |
| 映ったり途切れたりを繰り返す。ホストの `journalctl -u nvargus-daemon` に `PD_CRC_ERR: CRC error on packet payload` が多数出る | カメラのフラットケーブルの接触不良・損傷（CSI の転送エラー） | **電源を切ってから**ケーブルを両端とも挿し直す（端子の向き・ロックを確認）。改善しなければケーブルを交換。設定（jetson-io の `imx219-dual` など）ではこのエラーは起きません |
| 通知 `カメラに5回続けて接続できませんでした。カメラノードを再起動して接続し直します` | 接続の失敗が続いた（ケーブル、`nvargus-daemon` の再起動直後など） | 2 秒後に新しいプロセスで自動的に接続し直します。繰り返す場合は上の CRC エラーを確認 |
| `nvargus-daemon` を再起動した後、カメラがずっと `再接続中`。ログに `Failed to create CameraProvider` | 古い設定のコンテナ（`/tmp/argus_socket` をファイル単体でマウント）が、作り直された新しいソケットを見られない | `docker compose up -d` でコンテナを作り直す（現在の `docker-compose.yml` は `/tmp` ごと共有しているため、以後はデーモンを再起動しても自動で復帰します） |
| 画像が真っ黒 | レンズキャップ、極端に暗い環境 | キャップを外し、照明を確認。完全に同じ画像が続くとデータ保存は `カメラ画像が更新されていません（フリーズの可能性）` として記録しません |
| 画像が上下逆・左右逆 | カメラの取り付け向き | `config.yaml` の `camera.flip_method` を変更（2 = 180 度回転）。変更前に集めたデータとは向きが合わなくなる点に注意 |
| ダッシュボードの映像が粗い（320×128）、fps が 10 前後でカクつく・遅れる | 表示用プレビュー（640×360・15 Hz）が届かず、推論用の 320×128・10 Hz 画像を表示している（映像欄に「モデル入力と同じ画像」と表示）。ダミーカメラ使用時や `camera.preview_hz: 0` のときは正常 | `camera.preview_hz` が 0 でないか確認。実カメラなら「640×480・約 15 fps・表示用プレビュー」になります |
| 接続状況の取得 fps が大きく低い | Jetson の負荷が高い（学習を同時に実行しているなど） | 重い処理を止める |
| ダッシュボードの fps が 15 より大きく低い | ブラウザとの通信が遅い（Wi-Fi の電波など）。車両の制御には影響しません | ネットワーク環境を改善 |

## 4. コントローラー

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| ログ `【接続失敗】DualSenseコントローラーが見つかりません。USB接続かBluetoothペアリングの状態を確認してください。再接続を試行中です... (試行N回目: DualSense Wireless Controller is not found.)` | 未接続、電池切れ、ペアリングされていない | USB ケーブル（データ通信対応のもの）で接続するか、Bluetooth で接続する。1 秒ごとに自動で再接続を試みます |
| Bluetooth でつながらない | ペアリングしていない、または信頼（trust）していない | ホストで `bluetoothctl` を使い `scan on` → `pair <MAC>` → `trust <MAC>` → `connect <MAC>`。ペアリングモードは DualShock 4 が SHARE＋PS、DualSense が作成ボタン＋PS の長押し（ライトが点滅するまで） |
| ホストでは接続済みなのに見つからない | 古い設定のコンテナ（`/dev/input` を `devices` で渡していた頃のもの）のままで、再接続で増えた入力デバイスが見えていない | コンテナで `ls /dev/input` を確認。現在の `docker-compose.yml` はバインドマウントなので、`docker compose up -d` でコンテナを作り直せば解消します |
| 通知 `コントローラーとの接続が切れました。再接続を試みています（車両は安全停止します）` | 電池切れ、電波の届く範囲外、ケーブル抜け | 車両は自動で停止します（AUTO 中なら MANUAL に戻る）。再接続すると `コントローラーに再接続しました` と出ます。走行前に充電を確認 |
| 接続は正常なのにスティックやボタンに反応しない | 名前が一致する別の入力デバイス（タッチパッド・モーションセンサー）を掴んでいる可能性 | ダッシュボード接続状況のコントローラー欄に表示されるデバイスパスを確認。コントローラーを接続し直す |
| ボタンの割り当てが違う | イベントコードが想定（[仕様 9章](specification.md#9-コントローラーノード仕様)）と異なる | コンテナで `python3 -m evdev.evtest` を実行し、押したボタンのコードを確認 |
| 触っていないのにステアが少し動く | スティックのドリフトがデッドゾーン（0.05）を超えている | ダッシュボードのコントローラー入力で値を確認。コントローラーの交換を検討 |

## 5. 車両とシリアル通信

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| 接続状況の車両シリアルが `送信なし（DRY RUN）`。ログ `【シリアル警告】車両制御ポート /dev/ttyTHS1 をオープンできませんでした: …Permission denied…。シリアル送信なし（DRY RUNモード）で起動します。` | ポートの権限がない | ホストで `sudo chmod 777 /dev/ttyTHS1` を実行し、システムを再起動 |
| 同上で `No such file or directory` | コンテナに `/dev/ttyTHS1` がない | ホストで `ls -l /dev/ttyTHS1` を確認し、コンテナを作り直す |
| ログ `【シリアル警告】dry_run:=true が指定されたため、…` | launch 引数 `dry_run:=true` で起動した | 実車を動かすなら `dry_run:=true` を付けずに起動 |
| 車両が動かない | 原因を上流から順に切り分ける | ① ダッシュボードの「車両へ送信した値（PWM）」が操作に応じて変わるか。② 車両シリアルが `正常` か。③ Pi の端末に `Steering: …, Throttle: …, Brake: …, Shift: …` が出続けているか。④ ギア状態が `D（前進）` か（R2 を離していると N）。⑤ L2 を押していないか。⑥ 配線（TX→RX、GND の共通）とボーレート 115200 |
| Pi で `pigpio` 関連のエラーが出て受信プログラムが動かない | pigpio デーモンが起動していない | Pi で `sudo pigpiod` を実行してから受信プログラムを起動 |
| ブレーキがかかったまま（PWM `1135`） | Jetson 側で指令が 1 秒以上途絶え、ログに `【安全停止】操作指令が1秒以上届いていません。スロットル停止・フルブレーキを出力します。` | コントローラーの接続とダッシュボードの接続状況を確認。指令が戻ると `【安全停止解除】操作指令の受信を再開しました。` |
| 同上。Pi に `Warning: 0.5秒以上受信がないため、停止・フルブレーキにします` | Pi に有効な指令が届いていない（Jetson 停止、DRY RUN、ケーブル断） | Jetson が DRY RUN でないか、ケーブルを確認。受信が戻ると `Info: 受信を再開しました` |
| 同上。Pi に `Warning: チェックサム不一致のため N バイトを破棄しました` が出続ける | Pi は新しい受信プログラムだが、Jetson が古い（10 バイト形式の）送信ノード | Jetson のコードを最新にしてビルドし直す。車両はその間フルブレーキのまま（安全側） |
| 同上 | L2 が少し押されている、またはトリガーの戻りが悪い | ダッシュボードのコントローラー入力で L2 の値を確認 |
| 終了時や通信断でブレーキが**解放される** | Pi の受信プログラムが古い（起動時ブレーキ解放・受信タイムアウトなし） | 最新の `receiver_.py` を Pi にコピーして再起動（[仕様 7.4](specification.md#74-更新手順)） |
| Pi に `Warning: チェックサム不一致のため …` がたまに出る | 受信開始直後の途中データ、ノイズ | 起動直後の数回は正常。頻発する場合は配線・GND・ノイズ源を確認し、2 つ以上のシステムが同時に送信していないか確認 |

## 6. AUTO走行

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| 通知 `AUTOへの切替を拒否しました: コントローラー入力が途絶えています` | コントローラーが未接続、または操作解析ノードが停止 | コントローラーを接続（[4章](#4-コントローラー)）。接続状況の「操作解析」を確認 |
| 通知 `AUTOへの切替を拒否しました: 自動運転の操作量が届いていません（…）` | 制御ノードが操作量を出していない。理由はダッシュボードの「自動運転の制御」欄（`/control/status` の `reason`）に表示される | 下の行を参照 |
| 「自動運転の制御」が `仮の値で停止中`（`AUTO に必須のパラメータが仮の値（…）`） | タイヤ外周・ヨーレートの符号・操舵の対応表のいずれかを実測していない | `python3 tools/check_calibration.py` で確認し、実測して `config.yaml` の `unverified` から消す（[ユーザーマニュアル 3.10](../user_manual.md#310-仮の値未確定のパラメータの確認)） |
| 「自動運転の制御」が `waypoint が届いていない…` | モデル未読込・カメラ停止・推論ノード停止 | 「AI推論」「カメラ」の状態を確認 |
| 「自動運転の制御」が `車速が分からない…` | 車速センサーのノードが止まっている、外周が 0、IMU も車輪パルスもない | 「車速センサー」の状態と `wheel.circumference_m` を確認 |
| 「自動運転の制御」が `設定の誤り（vehicle.steer_table など）…` | `steer_table` の角度が指令に対して単調でない | `tools/steering_calibration.py` で作り直す |
| AUTO で、経路と逆の方向にハンドルを切る | `vehicle.steer_table` の符号、または `vehicle.yaw_sign` が逆 | すぐ SHARE で戻す。車輪を浮かせて、経路が左に曲がるときステア指令がマイナスになるか確認し、対応表と符号を確認し直す |
| AUTO で左右にふらつく / カーブの内側を回る | 注視距離が短すぎる / 長すぎる | `controller.lookahead_base_m` を大きく / 小さく（[ユーザーマニュアル 8.8](../user_manual.md#88-制御の調整)） |
| AUTO で目標速度に届かない・速度が波打つ | 速度制御のゲインが合っていない | `throttle_table`・`speed_kp`・`speed_ki` を調整（マニュアル 8.8） |
| ダッシュボードの予測経路が路面とずれて描かれる | `camera_geometry` が仮の値（凡例に `カメラの位置・向きは仮の値` と表示）、またはカメラの取り付けが動いた | カメラのキャリブレーション（[ユーザーマニュアル 10.9](../user_manual.md#109-カメラのキャリブレーション経路の重ね表示用)）。表示だけの問題で、制御には影響しない |
| （以前の文）`AUTOへの切替を拒否しました: 推論出力が届いていません（…）` | モデル未読込（走行モデル欄が `モデル未読込`） | `models/` にモデルがあるか、起動時に指定したモデル名が正しいか確認。ログの `【モデル未検出】…` / `【読込エラー】…` を確認 |
| 同上 | カメラ停止 | [3章](#3-カメラ) |
| 同上 | 推論ノードの停止 | 接続状況の「AI推論」が `応答なし` ならシステムを再起動 |
| ログ `【読込エラー】…: waypoint モデルの形式ではありません（旧形式の操作量モデルの可能性があります）` | 以前の操作量モデル（`model.pth` など、160×120 からステア・スロットルを出すもの）を指定した | `train_waypoint.py` で学習した waypoint モデルを指定する（既定は `models/waypoint.pth`） |
| ログ `画像サイズ …×… がモデルの入力（320×128）と違います` | `config.yaml` の `camera.resize` がモデルの入力と違う | `camera.resize` を `[320, 128]` に戻す |
| 通知 `AUTO走行を中断し、停止してMANUALに戻しました: <理由>` | AUTO 中にコントローラーまたは推論出力が 0.5 秒途絶えた | 理由の文を上の 2 行と同じように確認。車両は停止指令を受けて止まります |
| AUTO で走るがコースを外れる、ふらつく | データ不足・偏り、撮影時と照明や路面が違う、カメラの向きが変わった | `verify_h5.py --all` でデータ量と警告を確認し、同じ条件で走行データを追加して学習し直す。左右両方のカーブを含める |
| AUTO で止まらない・後退しない | 仕様（停止・後退は学習しない。AUTO 中のブレーキは常に解放） | 止めるときは SHARE で MANUAL に戻し、R2 を離して L2 を押す |
| 起動しただけで AUTO になる | `config.yaml` の `mux.default_mode` が `auto` | 意図しない場合は `manual` に戻す |
| ターミナルが `[Inference] …` のログで埋まる | `inference.verbose` が 1 以上だと画像ごとにログを出す | `config.yaml` の `inference.verbose` を 0 にして再起動 |

## 7. データ収集

### 7.1 「記録待機」の理由と対処

ダッシュボードの学習データ収集欄が `記録待機` のときは、理由が表示されます（ログでは `【データ保存】記録を停止中: <理由>`）。

| 表示される理由 | 意味 | 対処 |
| :--- | :--- | :--- |
| `起動待ち` | カメラ画像がまだ 1 枚も届いていない | カメラの状態を確認（[3章](#3-カメラ)） |
| `OPTIONSボタンで一時停止中` | 記録 OFF（ダッシュボードは `記録OFF` と表示） | OPTIONS を押して記録 ON に戻す |
| `走行モードが不明（MUXノードからの状態が届いていません）` | モード管理ノードが止まっている | 接続状況の「モード管理」を確認し、システムを再起動 |
| `AUTO走行中は記録しません` | 仕様（モデル自身の出力を学習データにしないため） | SHARE で MANUAL に戻す |
| `操作量が届いていません（コントローラー系の停止）` | `record_when: "throttle"` のときだけ。コントローラーの切断、または操作解析・モード管理ノードの停止で、操作量が 0.3 秒以上古い | コントローラーの接続を確認（[4章](#4-コントローラー)）。既定の `"moving"` では操作量がなくても記録します |
| `カメラ画像が更新されていません（フリーズの可能性）` | 直前と完全に同じ画像が届いた | カメラのフリーズは自動で復旧します。真っ黒な画像やレンズキャップも確認 |
| `後退中は記録しません` | 車速センサーが後退と判定している、またはシフトが R で R2 を押している | 前進で走る。前進なのに出る場合は `wheel.imu_forward_axis`（IMU の前方向）が合っていない（`tools/imu_forward_axis.py` で推定し直す） |
| `停止中` | 車速が 0.05 m/s 以下になって 2 秒以上たった | 走り出せば記録を再開します（止まっている間は記録しない仕様） |
| `車速が届いていません（車速センサーのノードの停止）` | `/wheel/status` が 0.3 秒以上届かない | 接続状況の「車速センサー」を確認（GPIO・配線） |
| `車速が不明です（外周が未設定、または起動直後）` | 外周が 0、または推定がまだ始まっていない | `wheel.circumference_m` を確認。起動直後なら少し待つ |
| `スロットルが閾値未満（停止中）` | `record_when: "throttle"` のときだけ。R2 の踏み込みが 5% 未満 | R2 を押して走行する |

### 7.2 その他

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| `data/` にファイルができない | ファイルは最初の 100 フレーム（10 Hz で約 10 秒）を書き出すとき、または終了時に作られる | 10 秒以上記録するか、`Ctrl + C` で終了する。ホストでは `/home/yl00/pius/data` を確認 |
| 記録したはずのフレームが足りない | `Ctrl + C` 以外の方法（ターミナルを閉じる、コンテナ停止など）で終了し、未書き出しのバッファ（最大 99 フレーム）が失われた | 終了は必ず `Ctrl + C` で行う |
| ファイル名の時刻がずれている | ファイル名はコンテナの時刻（UTC）で付けられる | 日本時間は 9 時間後 |
| `verify_h5.py` で `警告: 直前と完全に同一の画像が N フレームあります。カメラのフリーズ中に記録された可能性があります。` | フリーズ検出を入れる前に記録したデータ、または変換データにもともと同じ画像が含まれている | 件数が多いファイルは学習フォルダから外すか、撮り直す。現在の保存ノードはフリーズ中の画像を記録しません |
| `verify_h5.py` で `警告: ステアリングの操作値が完全に一定です。` / スロットルも同様 | 操作量が記録されていない（ダミーの `straight` パターンなど） | ダミーで作ったデータは学習に使わない |
| `verify_h5.py` の `【IMU/GPSチェック】` で `IMUの値があるフレーム` が 0 % または低い | 記録中に IMU / GPS センサーがつながっていなかった、または値が 0.3 秒より古かった（その間は NaN で記録） | IMU / GPS は任意のため、学習には影響しない。IMU の値も集めたい場合は [9章](#9-imu--gps) |
| `verify_h5.py` で `GPS測位中のフレーム` が 0 % | 屋内・アンテナなしなど、GPS が測位していなかった | 学習には影響しない。GPS の値が必要なら屋外でアンテナを付けて記録する |
| `verify_h5.py` で `高頻度データ（IMU 全サンプル・車輪パルス）の記録なし（フォーマットバージョン3以前、またはセンサー未接続）` | この機能より前のファイル、または記録中に IMU / GPS・車速センサーのどれも動いていなかった | 学習には影響しない。進路の正解データが必要なら、センサーをつないで記録し直す |
| `verify_h5.py` の `IMU 全サンプル` の周期（中央値）が 50 Hz ではなく 10 Hz 前後 | センサーが出荷時の出力頻度（10 Hz）のまま | [9.4](#94-出力設定を確認やり直すimu_configpy) で 50 Hz に設定し直す |
| `verify_h5.py` に `車輪パルス` の行が出ない | 記録中にパルスが 1 回もなかった（車速センサー未接続、`ERROR`、`use_wheel:=false`） | [10章](#10-車速センサー) |
| 高頻度データが、ファイルの最初のフレームより 10 秒以上前から始まっていない | 仕様。最初のフレームより前の高頻度データは、その直前 `save.pre_record_sec`（10 秒）分だけを残す | 対処不要。最初のフレーム以降の高頻度データはすべて記録されています |
| ダミーで起動したデータが混ざる | ダミー起動時も `data/` に保存される | 学習に使わないファイルは `data/` の外（例 `data/_backup/`）へ移す |

## 9. IMU / GPS

IMU / GPS センサー（WitMotion WTGAHRS3）は任意のセンサーです。以下のどの症状でも、**走行・モード切替・データ記録には影響しません**（記録される IMU / GPS の値が NaN になるだけです）。準備の手順は [ユーザーマニュアル 3.6](../user_manual.md#36-imu--gps-センサーの準備初回のみ)、仕様は [仕様 10章](specification.md#10-imugps-仕様) を参照してください。

### 9.1 センサーが認識されない（ホスト）

ホストで `ls -l /dev/ttyUSB* /dev/serial/by-id/` を実行し、`/dev/ttyUSB0` と `/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0` があるか確認します。

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| `/dev/ttyUSB0` ができない（`lsusb` には `1a86:7523` が表示される） | CH340 のドライバがインストールされていない。JetPack 6 のカーネルには CH340 のドライバ（`CONFIG_USB_SERIAL_CH341`）が含まれていない | ホストで `cd /home/yl00/pius/drivers/ch341 && make && sudo ./install.sh` を実行し、センサーを挿し直す。`lsmod \| grep ch341` で読み込まれたか確認できる |
| 以前は使えていたのに `/dev/ttyUSB0` ができなくなった | `apt upgrade` などでカーネル（`nvidia-l4t-kernel`）が更新され、ドライバが読み込まれなくなった | 同じフォルダで `make clean && make` → `sudo ./install.sh`。カーネルのバージョン番号が変わった場合は、`drivers/ch341/README.md` の手順で対応するソースに差し替えてからビルドする |
| `sudo ./install.sh` で `ch341.ko はカーネル … 用です（実行中のカーネルは …）。make clean && make で再ビルドしてください。` | 前のカーネルでビルドした `ch341.ko` が残っている | 表示どおり `make clean && make` してから `sudo ./install.sh` |
| `sudo ./install.sh` で `ch341.ko がありません。先に make を実行してください。` | `make` をしていない | `make` を実行してから `sudo ./install.sh` |
| `/dev/ttyUSB0` が一瞬できてすぐ消える（ホストの `sudo dmesg` に `brltty` の文字） | 点字ディスプレイ用のサービス `brltty` が CH340 を自分の機器とみなして横取りしている | `sudo ./install.sh` を実行する（`brltty` を無効化します）。すでにインストール済みなら `sudo systemctl mask brltty-udev.service brltty.service` を実行してセンサーを挿し直す |
| `make` で `the compiler differs from the one used to build the kernel` という警告 | Ubuntu の gcc のパッチ版数の違い | 問題ない。そのまま `sudo ./install.sh` へ進む |
| `lsusb` にも `1a86:7523` が表示されない | USB ケーブルの接触不良、充電専用ケーブル、センサーの電源が入っていない | ケーブルを交換・挿し直す。別の USB ポートを試す |

### 9.2 ダッシュボード・ログでの症状

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| 接続状況の IMU/GPS が `再接続中` のまま。ログ `【IMU】ポート /host_dev/serial/by-id/usb-1a86_USB_Serial-if00-port0 を開けません。センサーの接続を確認してください。再接続を試行中です... (…)` | センサーが抜けている、またはホストで認識されていない | [9.1](#91-センサーが認識されないホスト) でホスト側を確認。挿し直せば 1 秒以内に自動で再接続し、`IMUに再接続しました`（初回は `IMUのポートを開きました`）と通知が出る |
| 同上。ホストでは `/dev/serial/by-id/` にセンサーがあるのに再接続できない | コンテナが IMU 対応前の `docker-compose.yml` で作られたまま（ホストの `/dev` が `/host_dev` に見えない、USB シリアルへのアクセス許可がない） | コンテナで `ls /host_dev/serial/by-id/` を確認。`/host_dev` がなければ、ホストで `docker compose up -d` を実行してコンテナを作り直す（`start_system.sh` でも自動で作り直される）。ログの末尾が `Permission denied` の場合も同様 |
| 同上。別の USB シリアル機器を使っている | センサーの `/dev/serial/by-id/` の名前が `config.yaml` の `imu.port` と違う | ホストで `ls /dev/serial/by-id/` の名前を確認し、`imu.port` を `/host_dev/serial/by-id/<その名前>` に合わせて再起動 |
| IMU/GPS が `データなし`。通知 `IMUからデータが届いていません（ボーレート設定 115200 を確認してください）` | ポートは開けたが、1 秒以上正しいデータが届かない。センサーの通信速度と `config.yaml` の `imu.baudrate`（115200）が合っていない。`tools/imu_config.py --factory-reset` や WitMotion の公式アプリで工場出荷状態（9600 bps）に戻した、または新しいセンサー（出荷時 9600 bps）に交換した可能性が高い | [9.4](#94-出力設定を確認やり直すimu_configpy) の `--show` で通信速度を確認し、`--apply` で 115200 bps・50 Hz に設定し直す。9600 bps のまま使う場合は `imu.baudrate` を `9600` にして再起動 |
| 通知 `IMUとの接続が切れました。再接続を試みています（走行には影響しません）` | 走行中の振動などで USB が抜けた・瞬断した | 自動で再接続し `IMUに再接続しました` と出る。頻発する場合はケーブルとコネクタを固定する |
| IMU/GPS が `起動待ち` のまま。IMU / GPS 欄に `IMUノードが起動していません（use_imu:=false の可能性）` | `use_imu:=false` で起動した、または更新後に再ビルドしていない | IMU を使うなら `use_imu:=false` を付けずに起動する。コンテナで `colcon build` → `source install/setup.bash` をしてから起動し直す |
| IMU/GPS が `応答なし` | IMU ノードが異常終了した | 2 秒後に自動で再起動する。繰り返す場合はターミナルの `Traceback` を確認 |
| GPS が `未測位` のまま（衛星数 0、HDOP が 31.2 など大きい値） | 屋内、アンテナが接続されていない、空が見えない場所。電源投入直後 | 屋外の空が開けた場所に出て、アンテナを接続して待つ（屋外でも測位まで数十秒、条件によっては数分）。屋内では測位しないのが正常で、故障ではない |
| 姿勢・加速度の値がおかしい。注意書きが赤で `角速度が測定範囲（±500°/s）に達しました。姿勢・加速度の値がしばらく不正確になる可能性があります`（同じ文の WARN 通知も出る） | センサーを手で素早く回したりひっくり返したりして、角速度が測定範囲（±500 °/s）を超え、センサー内部の姿勢計算が狂った。故障ではない | しばらくセンサーを静止させる。ロール・ピッチは重力を基準に少しずつ正しい値へ戻る。**ヨーは戻らない**（地磁気センサーがなく基準がない）ので、USB を挿し直してセンサーの電源を入れ直す（またはロック解除 `FF AA 69 88 B5` のあと `FF AA 01 04 00` を送ってヨーを 0 にする）。時速約 5 km で走る車両ではまず起こらない |
| 素早く回した後、ロール・ピッチは戻ったのにヨーだけずれたまま | 上と同じ。ヨーには戻す基準がない | USB を挿し直す（上と同じ） |
| ヨー（方位）が走行中に少しずつずれていく | このセンサーには地磁気センサーがなく、ヨーは角速度の積算で求めるため | 仕様。止まっている間は静止判定でずれない。走行中の向きは、GPS 測位中であれば進行方向（GPS）も参考にする |
| ヨーが一瞬で数度〜数十度跳ぶ | センサー内部の補正（GPS の進行方向による方位の更新など） | 仕様。記録したデータから向きの変化を求めるときは、角速度 Z の積分と照らし合わせて跳びを除外する（[仕様 12.4](specification.md#124-高頻度データimu_hr--gps_hr--wheel)） |
| 接続状況の IMU/GPS が `OK` だが Hz が 50 ではなく 10 前後（例 `10Hz・GPS未測位（衛星0）`） | センサーが出荷時の出力頻度（10 Hz）のまま（`imu.baudrate` を 9600 にして使っている） | [9.4](#94-出力設定を確認やり直すimu_configpy) で `--apply` を実行し、`imu.baudrate` を `115200` に戻す |

### 9.3 センサー単体で確認する

走行システムと切り離してセンサーだけを確認するときは `tools/witmotion_check.py` を使います。ホストには pyserial が入っておらず、シリアルポートの権限（`dialout` グループ）もないため、コンテナのイメージを使って実行します。走行システムは `Ctrl + C` で止めてから、ホストで実行してください（`Ctrl + C` で終了）。

```bash
# 現在の設定（115200 bps）。末尾がボーレート
docker run --rm -it --device /dev/ttyUSB0 --group-add 20 -v /home/yl00/pius:/ws namazyake/roscar2:cu126 python3 /ws/tools/witmotion_check.py /dev/ttyUSB0 115200
# 工場出荷状態のセンサー（9600 bps。ボーレートを省略したときの既定値）
docker run --rm -it --device /dev/ttyUSB0 --group-add 20 -v /home/yl00/pius:/ws namazyake/roscar2:cu126 python3 /ws/tools/witmotion_check.py /dev/ttyUSB0
```

| 表示 | 見方 |
| :--- | :--- |
| `受信パケット: 正常 N / チェックサム異常 M` | 正常の数が増えていけば受信できている。正常が 0 のままチェックサム異常だけ増える場合はボーレートが合っていない |
| `受信した種類` | 受信したデータの種類（`51` 加速度、`52` 角速度、`53` 角度、`57` 経度・緯度、`58` GPS 高度・方位・速度、`59` 四元数、`5A` 衛星数・精度）。現在の設定では `51` `52` `53` `57` `58` `5A` の 6 種類（`59` は出力しない） |
| `※ 正常なパケットが届いていません。ポート名・ボーレート・配線を確認してください。` | ポート名・ボーレート・ケーブルを確認 |
| 加速度・角速度・角度 | センサーを傾けると値が変わることを確認。水平に置くと加速度の Z が約 1 g |
| `衛星数 N  PDOP … HDOP … VDOP …` | 屋外で衛星数が 4 以上になれば測位できる |

Windows の PC に直接つないで確認することもできます（`pip install pyserial` のあと `python witmotion_check.py COM3`。COM 番号はデバイスマネージャーで確認）。

システムが動いている状態では、コンテナで次のコマンドでも値を確認できます。

| 確認するもの | コマンド |
| :--- | :--- |
| 姿勢・加速度・角速度・GPS のまとめ（JSON、10 Hz） | `ros2 topic echo /imu/status` |
| IMU（`sensor_msgs/Imu`、約 50 Hz） | `ros2 topic echo /imu/data`（周期は `ros2 topic hz /imu/data`） |
| GPS（`sensor_msgs/NavSatFix`、約 50 Hz） | `ros2 topic echo /gps/fix` |
| 状態（`imu:OK:50Hz・GPS未測位（衛星0）` など） | `ros2 topic echo /system/health \| grep imu` |

### 9.4 出力設定を確認・やり直す（imu_config.py）

センサーは `tools/imu_config.py --apply` で **50 Hz・115200 bps** に設定して保存してあります（出荷時は 10 Hz・9600 bps）。設定を確認・やり直すときは、走行システムを `Ctrl + C` で止めてから、ホストで次を実行します（仕様は [仕様 10.9](specification.md#109-出力設定の変更toolsimu_configpy)）。

```bash
docker run --rm -it --device /dev/ttyUSB0 --group-add 20 -v /home/yl00/pius:/ws namazyake/roscar2:cu126 python3 /ws/tools/imu_config.py --show
# 設定し直すときは --show を --apply に、出荷時に戻すときは --factory-reset に変える
```

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| `センサーからデータが届きません。接続と、他のプログラムがポートを使っていないかを確認してください。` | 走行システム（`imu_node`）や `witmotion_check.py` がポートを使っている、またはセンサーがつながっていない | 走行システムを止めてから実行する。[9.1](#91-センサーが認識されないホスト) でホスト側の認識を確認 |
| `--apply` で `新しい通信速度でデータが届きません。--show で状態を確認するか、--factory-reset で元に戻してください。` | 通信速度の変更後に、115200 bps でデータが届かなかった | USB を挿し直してから `--show` で状態を確認。直らなければ `--factory-reset` で戻してから `--apply` をやり直す |
| USB を挿し直したら 9600 bps・10 Hz に戻っていた | 設定がセンサーに保存されなかった | もう一度 `--apply` を実行し、USB を挿し直して `--show` で確認する |
| `--factory-reset` の後、ダッシュボードの IMU/GPS が `データなし` | センサーが 9600 bps に戻り、`imu.baudrate`（115200）と合わなくなった | `--apply` で 115200 bps・50 Hz に設定し直すか、`imu.baudrate` を `9600` にして再起動 |

## 10. 車速センサー

車速センサー（後輪左のリードスイッチ、74HC14 バッファ基板経由で 40 ピンヘッダの 7 番ピン）は任意のセンサーです。以下のどの症状でも、**走行・モード切替・データ記録には影響しません**（記録される車速の値が NaN になるだけです）。準備の手順は [ユーザーマニュアル 3.8](../user_manual.md#38-車速センサーの準備初回のみ)、仕様は [仕様 11章](specification.md#11-車速センサー仕様) を参照してください。

### 10.1 ダッシュボード・ログでの症状

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| 接続状況の車速センサーが `起動待ち`。車速（車輪）欄に `センサーのノードが起動していません` | `use_wheel:=false` で起動した、または更新後に再ビルドしていない | 車速センサーを使うなら `use_wheel:=false` を付けずに起動する。コンテナで `colcon build` → `source install/setup.bash` をしてから起動し直す |
| 車速センサーが黄色の `ERROR`、バナー `車速センサー: GPIO を使えません: …（走行・記録には影響しません）`。`…` に `Device or resource busy` | 別のプログラムが同じピン（BOARD 7 番）を使っている。ホストで `tools/speed_sensor_check.py` を動かしたまま、または別の launch がコンテナ内で動いている | そのプログラムを `Ctrl + C` で止め、システムを再起動する（車速センサーのノードは GPIO の再試行をしないため、再起動が必要） |
| 同上。`…` に `No module named 'Jetson'` | コンテナが車速センサー対応前の `docker-compose.yml` で作られたまま（ホストの Jetson.GPIO がマウントされていない）。またはホストに Jetson.GPIO がない | ホストで `docker compose up -d` を実行してコンテナを作り直す（`start_system.sh` でも自動）。ホストに `/usr/lib/python3/dist-packages/Jetson` があるか確認 |
| 同上。`…` に `Could not determine Jetson model` | コンテナに環境変数 `JETSON_MODEL_NAME` がない（コンテナの中では `/proc/device-tree` が見えず、ボードを判定できない） | 上と同じくコンテナを作り直す。コンテナで `echo $JETSON_MODEL_NAME` が `JETSON_ORIN_NANO` になるか確認 |
| 同上。`…` に `The current user does not have permissions …` | コンテナに `/dev/gpiochip0`・`/dev/gpiochip1` が渡されていない、または gpio グループ（999）に入っていない | 上と同じくコンテナを作り直す。ホストで `ls -l /dev/gpiochip*` のグループが `gpio`、`getent group gpio` の番号が 999 であることを確認（違う場合は `docker-compose.yml` の `group_add` を合わせる） |
| 車速（車輪）が `外周未設定（config.yaml の wheel.circumference_m）`、状態の末尾に `・外周未設定` | `config.yaml` の `wheel.circumference_m` が 0.0（未設定、既定値） | 後輪左のタイヤの外周を実測して設定し、再起動（[ユーザーマニュアル 3.8](../user_manual.md#38-車速センサーの準備初回のみ)）。未設定の間もパルスは記録されている |
| 車速（車輪）が `不明（パルス2回目から計算）` | 起動後・停止後、2 回目のパルスが来るまでは速度を計算できない | 仕様。動き出してタイヤが 2 回転すると表示される。走っているのに変わらないときは下の行 |
| 車輪を回しても `累計 N パルス` が増えない | 配線の誤り・断線、74HC14 基板の電源が来ていない、磁石がスイッチから離れすぎている | システムを止めてから、ホストで `python3 tools/speed_sensor_check.py --raw` を実行し、磁石を近づけたときに `レベル 1`、離したときに `レベル 0` になるか確認する。変わらなければ配線（1 番 3.3 V・7 番 信号・9 番 GND）と磁石の位置を確認。**2 番・4 番（5 V）には絶対につながない** |
| ゆっくり走っているのに `0.0 km/h` | 3 秒（`wheel.stop_timeout_sec`）以上パルスがないと停止とみなす。外周 1.5 m なら約 1.8 km/h 未満 | 仕様。低速まで測りたい場合は `stop_timeout_sec` を長くする |
| 速度が実際と比例してずれる（いつも 1 割多いなど） | `wheel.circumference_m` の値が実際の外周と違う | 外周を測り直して設定する |
| 1 回転で 2 回以上数えられる（速度が倍以上になる） | スイッチのチャタリングやケーブルのノイズが、チャタリング除去（100 ms）より長く続いている | `--raw` で波形の様子を確認。シールドのドレイン線が基板側の GND だけにつながっているか確認。必要なら `wheel.debounce_ms` を大きくする（その分、測れる上限速度が下がる） |

### 10.2 確認スクリプト（speed_sensor_check.py）での症状

| 症状 | 考えられる原因 | 対処 |
| :--- | :--- | :--- |
| `Device or resource busy` のエラーで終了する | 走行システム（`wheel_speed_node`）が同じピンを使っている | 走行システムを `Ctrl + C` で止めるか、`use_wheel:=false` で起動してから実行する |
| `The current user does not have permissions set to access the library functionalites. …` | 実行ユーザーが `gpio` グループに入っていない | `sudo usermod -aG gpio <ユーザー名>` のあと、ログインし直す（`id` の出力に `gpio` があれば OK） |
| `まだパルスがありません` のまま | 配線、または磁石の位置 | `--raw` で配線を確認（上の表） |

システムが動いている状態では、コンテナで次のコマンドでも値を確認できます。

| 確認するもの | コマンド |
| :--- | :--- |
| 推定車速・累計パルス数（JSON、10 Hz） | `ros2 topic echo /wheel/status` |

| 状態（`wheel:OK:5.2km/h・累計128パルス` など） | `ros2 topic echo /system/health \| grep wheel` |

## 11. ログの集め方

問題を報告・相談するときは、次の情報をそろえると原因を特定しやすくなります。

| 情報 | 集め方 |
| :--- | :--- |
| ターミナルの出力 | `start_system.sh` を起動した端末の出力をコピーする。最初から保存するには `./start_system.sh 2>&1 \| tee pius_$(date +%Y%m%d_%H%M%S).log` |
| 起動 15 秒後のサマリー | ターミナルに出る `【 PIUSシステム 接続健全性サマリー 】` の部分 |
| ROS のログファイル | コンテナの `~/.ros/log/`（`/home/orin/.ros/log/`）。コンテナを作り直すと消えるので、ホストで `docker cp roscar2:/home/orin/.ros/log ./ros_log` でコピー |
| 各ノードの状態 | コンテナで `ros2 topic echo /system/health` |
| IMU / GPS の値 | コンテナで `ros2 topic echo /imu/status` |
| 車速センサーの値 | コンテナで `ros2 topic echo /wheel/status` |
| 通知の履歴 | コンテナで `ros2 topic echo /system/notice`（ダッシュボードの「通知」欄にも直近の履歴があります） |
| 動作中のノード | コンテナで `ros2 node list` |
| モード・記録・送信値 | `ros2 topic echo /mux/mode`、`/save/status`、`/vehicle/pwm` |
| ダッシュボードの状態一式 | `curl http://localhost:8080/api/state`（ホストまたはコンテナ） |
| Raspberry Pi 側 | 受信プログラムの端末出力（`Warning: …` / `Info: …` の行） |
| 収集データ | `python3 verify_h5.py --all` の出力 |

コンテナで `ros2` コマンドを使う前に `source /home/orin/dev/ws/colcon_ws/install/setup.bash` を実行してください。
